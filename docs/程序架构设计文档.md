## 1. 合并目标

将两个参考项目的业务合并到一个 Avalonia 桌面程序中，形成三大业务板块：

| 板块 | 来源 | 核心能力 |
|---|---|---|
| **文档审核** | AiAuditDemo-main | 导入 DOCX 维修文档 → AI 多模态审核（对照标准文档+补充条款）→ 审核意见回写 DOCX（标红/书签/超链接） |
| **知识库** | 叶片缺陷审核qt版 | 文档导入存档（PDF 走图片识别）→ 关键词检索（加权评分 RAG）→ AI 问答（多模态附图） |
| **缺陷文档生成** | 叶片缺陷审核qt版 | 输入缺陷信息 → Agent 流水线（规划→撰写→审校）→ 生成真 .docx（封面+目录+正文） |

共用底座：**统一 LLM 网关（OpenAI 兼容协议）+ 多模型配置管理 + 机器授权 + 统一 UI 框架**。

## 5. 服务层设计

### 5.1 ILLMService — 统一 LLM 网关（合并 A 的 ModelService + B 的 LLMService）

```
// 配置
Task<bool> TestConnectionAsync(LlmModelConfig config, CancellationToken ct)
IReadOnlyList<LlmModelConfig> Models            // 多套具名配置
LlmModelConfig? Current                          // 当前启用（唯一）
event: 添加/删除/切换模型 → 持久化 llm_config.json

// 调用（OpenAI 兼容 /chat/completions）
Task<string> SendAsync(IReadOnlyList<LlmMessage> messages, string? systemPrompt, CancellationToken ct)
IAsyncEnumerable<string> SendStreamAsync(...)    // SSE 流式：data:{delta.content}
void Cancel()

// LlmMessage.Content = 多 part：{type:"text"} + {type:"image_url"(dataURI,≤6MB)}
```

- 内置厂商预设：通义千问（DashScope compatible-mode）、DeepSeek、OpenAI、Kimi、智谱 GLM。
- **API Key 只存本地 llm_config.json，移除参考项目中的硬编码 Key。**

### 5.2 IAppConfigService — 配置服务（含领域字段清单）

- 读写 appsettings.json 中 `DomainFields` 节（替代 A 中硬编码的字段清单）：
  `["维修过程描述","质量控制","施工内容","拍摄时间","叶片重量","施工人员","施工日期","机位号","叶片套号","生产日期"]`
- 供审核管线（回写匹配）与生成服务共同引用；支持运行期修改并保存。

### 5.3 知识库（迁自 B，逻辑不变）

### 5.4 文档导入（B 的 DocImporter，C# 重写）

- docx → NPOI 提取纯文本；xlsx/csv → 库解析；txt/md → 直读。
- **PDF → 仅存档**：导入时提取文件名作为标题（可手动补标签），**不解析正文、不识别**；条目标记 `archiveType=pdf`。正文文字在检索命中后按需识别（§5.7）。
- 图片 → 存档 + 缩略图；`FileToDataUrl(path, maxBytes)` 供多模态附图。

### 5.5 缺陷文档生成（B 的 AgentService + 新增 DocxBuilder）

```
IDocGenAgentService
  IAsyncEnumerable<AgentStep> GenerateAsync(DocGenInput input, CancellationToken ct)
  // 步骤1 规划：输出 {title, sections[]} JSON（失败回退内嵌模板结构）
  // 步骤2 撰写：正文内容（章节+表格结构化输出）
  // 步骤3 审校：表格序号/题注修正、内容一致性检查；失败回退草稿
```

```
IDocxBuilderService   // 【新】模型 Word-HTML → 真 .docx（Open XML SDK + HtmlToOpenXml）
  Task<string> BuildAsync(DocGenDocument doc, DocGenStyle style, CancellationToken ct)
```

**生成策略（模型 API 不支持直接输出 .docx，采用"模型产内容+本地转换"混合路线）**：

| 环节 | 承担方 | 说明 |
|---|---|---|
| 正文内容 + 内联样式 | LLM（Kimi/通义 VL 系列） | 撰写步骤输出 Word-HTML（复用 B 项目已验证的 prompt：office 命名空间、内联样式、表格结构、禁止图片） |
| HTML → docx 正文 | HtmlToOpenXml.dll（开源 MIT） | 解析模型 HTML 为 OpenXML 段落/表格 |
| 表格样式统一 | 本地确定性后处理 | **不信任模型边框细节**：按 style 选项重刷三线表/全框线边框；题注连续编号校验重排 |
| 封面页 + 目录页 | 本地代码 | 复刻 B 的封面版式（标题+编制/审核/批准/版本签名表）；目录页插入 Word **TOC 域代码**（`TOC \o "1-3" \h`），打开文档时更新页码 |

- **docx 结构**（按顺序）：封面页 → 目录页（TOC 域）→ 正文（Heading1-3 映射大纲级别，供 TOC 抓取；段落；表格+题注）。
- 样式来源优先级（沿用 B）：内嵌参考模板 `reference_template.docx`（解析标题/正文字号、表格样式作为 HTML 生成约束注入 prompt）> 导入 docx 提取 > 手动输入 > 默认。
- 原 Word-HTML 存 `.doc` 方案废弃；NPOI 仅用于审核管线的提取与回写，生成链路用 Open XML SDK。

### 5.6 ILicenseService — 授权服务（新，替代 A 的 password.json 方案）

```
ILicenseService
  bool IsLicensed()                        // 授权文件存在且有效
  ActivationResult Activate(string phone)  // 首次激活：生成授权文件+派生密码
  bool Login(string phone, string password) // 登录校验
  string CurrentPhone { get; }
```

**授权流程**：
1. **激活**：用户输入手机号 → 读取本机 MAC（取首块物理网卡，规范化小写去分隔符）→
   派生密钥 `PBKDF2(phone + mac, salt=固定应用盐)` → **AES 加密** `LicenseInfo{phone, macHash, createdAt}` → 写 `%AppData%/叶片缺陷审核/license.dat` →
   从授权文件字节派生登录密码 `HMAC-SHA256(licenseBytes, phone) → 格式化 8 位（如 XXXX-XXXX）` → **界面显示该密码供用户记录**。
2. **登录**：用户名=手机号，密码=激活时派生的密码。校验：重算 HMAC 与输入一致 + 解密授权文件校验 MAC 与本机一致（**机器绑定，换机需重新激活**）。
3. **失效/重置**：删除 license.dat 即可重新激活；登录页提供"重新激活"入口。

> 安全说明：该方案为机器绑定的防误用措施（与 KN1 授权思路同级别），非强加密保护；MAC 可被仿冒，如需更强防护后续可换硬件指纹（主板序列号+磁盘序列号）或在线激活。

### 5.7 IPdfRecognizeService — PDF 按需识别（新）

```
IPdfRecognizeService
  Task<PdfRecognizeResult> RecognizeAsync(string pdfPath, IProgress<string> log, CancellationToken ct)
```

**触发时机（按用户决策）**：仅当知识库检索**标题/标签命中** PDF 条目且该条目尚无识别文本时，由 `KnowledgeBaseService.EnsureContentAsync` 触发识别；导入时不识别。

流程：
1. **转图**：PdfiumViewer 每页渲染为 PNG（150DPI，与预览管线共用）。
2. **识别**：逐页（或合并至批量上限）以 `{type:"image_url"}` 多模态消息调 `ILLMService`，prompt 要求输出该页的纯文本结构（标题/段落/表格行），模型用当前启用的 VL 模型（如 qwen-vl-plus）。
3. **输出与缓存**：拼接为结构化文本 → 返回 `PdfRecognizeResult{Pages: [{pageIndex, text}], FullText}` → **回写知识库条目 content 字段持久化**，后续检索/问答直接复用，不再重复调用。
- 费用提示：识别消耗 LLM tokens（仅在标题命中时发生），界面显示进度（第 x/N 页）与"正在识别 PDF"状态。

## 6. 核心业务流程

### 6.1 授权登录（新）
```
启动 → 已有有效授权文件？ → 是：登录窗口（手机号+密码）
                              → 否：激活窗口（输入手机号 → 生成授权+显示密码）
```

### 6.2 文档审核（来源 A）
```
拖入 DOCX → 选标准文档 + 填补充条款 → [预览] DOCX→PNG
→ [AI审核] 提取→prompt组装(领域字段来自配置)→LLM→解析JSON→回写DOCX（标红/书签/页尾意见）
→ 界面显示【原文/问题/建议】 → 刷新预览复核
```

### 6.3 知识库问答（来源 B，PDF 按需识别链路）
```
导入文档建库（PDF 仅存档标题/标签，不识别）→ 输入问题 → 关键词检索 Top6
→ PDF 条目标题/标签命中 → 按需触发：PDF→转图→多模态识别→文本回写缓存
→ 命中文本拼 RAG 上下文 + 图片命中转附图（≤3张）→ LLM 流式回答
```

### 6.4 缺陷文档生成（来源 B + 升级）
```
填写缺陷信息（位置/布层数/材料/损伤程度）→ 选格式来源
→ Agent 步骤 1/3 规划 → 2/3 撰写 → 3/3 审校
→ DocxBuilder 生成真 .docx：封面页 → 目录页(TOC域) → 正文(标题/表格/题注)
→ 预览 → 保存
```

| 2 | PDF 识别质量 | 依赖 VL 模型能力，扫描件表格结构可能失真；**按需识别**（仅标题命中后触发），识别结果缓存回写条目，token 成本可控；首次命中会有"识别中"等待（逐页显示进度） |
| 3 | TOC 目录页 | 使用 Word 域代码，页码需 Word 打开时更新（自动/提示更新域）；NPOI 无法预知分页 |
| 4 | 真 .docx 生成 | 模型 API 无文件输出端点，采用"模型产 Word-HTML + HtmlToOpenXml 本地转真 .docx"；表格边框/题注编号由本地确定性后处理保证；目录页页码需 Word 打开时更新域 |
| 5 | API Key 本地明文 | 与参考项目一致，接受风险（可后续 DPAPI 加密） |

## 12. 文档生成：开源 Agent 选型（用户提问解答）

**结论：有通用的开源 Agent 框架，但没有"专做 Word 文档生成"的开箱即用 Agent。** 我们的生成流程本质是固定三步流水线（规划→撰写→审校），prompt 资产（B 项目已验证）才是核心价值，框架只负责编排。可选：

| 方案 | 类型 | 优劣 | 适用性 |
|---|---|---|---|
| **自研轻量编排**（推荐） | 顺序 Workflow（复用 B 逻辑） | 零新增依赖、prompt 已验证、代码量小（~200 行） | 本项目三步固定流程完全够用 |
| **Microsoft Agent Framework**（MAF） | 微软开源 C# Agent 框架（Semantic Kernel + AutoGen 合并，GitHub 7k+ stars） | .NET 原生、Workflows 编排/checkpoint/人在环/可观测；引入依赖，学习成本中等 | 如需多 Agent 协作、工具调用、流程中断恢复时选它 |
| Semantic Kernel | 微软开源 C# | 成熟稳定，偏 SDK 而非 Workflow | 与 MAF 二选一 |
| Dify / LangGraph / n8n | Python/服务端平台 | 功能强但需独立部署服务，不适合内嵌桌面程序 | 不采用 |

**建议**：一期用**自研轻量编排**（`IDocGenAgentService` 顺序三步 + 步骤事件上报 UI），接口设计预留扩展点（步骤可插拔）；若后续需要"检索知识库 → 生成 → 审核 → 回写"的多 Agent 协作，再引入 **Microsoft Agent Framework**（NuGet: `Microsoft.Agents.AI` / `Microsoft.Agents.AI.Workflows`），届时三步 prompt 可原样迁入。
